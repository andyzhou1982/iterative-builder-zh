# 代码审查

对迭代项目的单个阶段进行全面代码审查。

## 审查流程

```
Day N 代码
    |
    v
[逐文件扫描]
    |
    v
[分类审查] → 代码质量 / 架构 / 安全 / 性能 / 可维护性
    |
    v
[生成报告]
    |
    v
[修改建议] + [跨阶段影响分析]
```

## 第一步：确定审查范围

### 1.1 扫描目标目录

扫描指定 Day 的目录结构，识别所有源代码文件：

```
dayN/
├── backend/
│   ├── src/
│   └── test/
├── frontend/
│   └── src/
└── ...
```

### 1.2 排除规则

以下文件不需要审查：
- 第三方依赖（node_modules/, venv/, vendor/）
- 自动生成文件（dist/, build/, __pycache__/）
- 配置文件（package.json, tsconfig.json）
- 模板文件（*.html 模板）

## 第二步：分类审查

对每个源代码文件进行以下五个维度的审查。

### 2.1 代码质量

检查项：
- **命名规范** - 变量、函数、类命名是否清晰一致
- **函数长度** - 单个函数是否过长（建议不超过 50 行）
- **代码重复** - 是否有可提取的公共逻辑
- **错误处理** - 异常是否被正确捕获和处理
- **双语注释** - 是否按照 [bilingual-comments.md](references/bilingual-comments.md) 格式

### 2.2 架构设计

检查项：
- **层次分离** - 前端/后端/数据层是否清晰分离
- **依赖方向** - 是否遵循依赖规则（不反向依赖）
- **接口设计** - API 接口是否 RESTful、一致
- **数据模型** - 数据结构是否合理、可扩展

### 2.3 安全性

检查项：
- **输入验证** - 用户输入是否验证和清理
- **SQL 注入** - 是否使用参数化查询
- **XSS 防护** - 前端是否转义用户输入
- **认证授权** - 敏感操作是否有权限检查
- **密钥管理** - 是否有硬编码的密钥或凭证

### 2.4 性能

检查项：
- **数据库查询** - 是否有 N+1 查询、缺少索引
- **内存使用** - 是否有大对象未释放、内存泄漏风险
- **缓存策略** - 是否有合理的缓存机制
- **异步处理** - 耗时操作是否异步化

### 2.5 可维护性

检查项：
- **配置管理** - 配置是否外置（环境变量/配置文件）
- **日志记录** - 关键操作是否有日志
- **测试覆盖** - 是否有对应的测试文件
- **文档完整** - README、API 文档是否齐全

## 第三步：生成审查报告

### 报告格式

```markdown
# 代码审查报告: Day N

## 概要

| 维度 | 评分 | 问题数 |
|------|------|--------|
| 代码质量 | ⭐⭐⭐⭐ | 2 |
| 架构设计 | ⭐⭐⭐⭐⭐ | 0 |
| 安全性 | ⭐⭐⭐ | 3 |
| 性能 | ⭐⭐⭐⭐ | 1 |
| 可维护性 | ⭐⭐⭐⭐ | 2 |

## 问题列表

### 🔴 严重问题

#### 1. [问题标题]
- **文件**: `backend/src/services/user.py:42`
- **类别**: 安全性
- **描述**: [问题描述]
- **建议**: [修改建议]
- **代码示例**:
  ```python
  # 当前代码
  ...

  # 建议修改
  ...
  ```

### 🟡 建议改进

#### 2. [问题标题]
- **文件**: `frontend/src/components/List.tsx:15`
- **类别**: 性能
- **描述**: [问题描述]
- **建议**: [修改建议]

### 🟢 值得肯定
- [好的实践 1]
- [好的实践 2]
```

## 第四步：跨阶段影响分析

如果审查发现需要修改代码，必须分析修改是否影响其他阶段：

1. **识别共享代码** - 被审查文件中是否有其他 Day 依赖的公共模块
2. **分析修改范围** - 建议的修改是否会改变接口或数据结构
3. **评估传播影响** - 修改传播到其他 Day 的可能性

### 影响分析格式

```markdown
## 跨阶段影响分析

| 修改项 | 影响的 Day | 影响说明 | 需要操作 |
|--------|-----------|---------|---------|
| 接口参数变更 | Day 3, Day 4 | 调用方需同步修改 | ✅ |
| 工具函数修复 | Day 2 | 已复制相同代码需修复 | ✅ |
| 样式优化 | - | 仅限当前 Day | ❌ |
```

## 审查标准

### 严重程度定义

| 级别 | 标记 | 定义 |
|------|------|------|
| 严重 | 🔴 | 必须修复：安全漏洞、数据丢失风险、功能缺陷 |
| 建议 | 🟡 | 建议修复：性能问题、可维护性差、不符合最佳实践 |
| 肯定 | 🟢 | 值得保留：好的设计模式、清晰的代码 |

### 评分标准

| 星级 | 含义 |
|------|------|
| ⭐⭐⭐⭐⭐ | 优秀，无需改进 |
| ⭐⭐⭐⭐ | 良好，有少量建议 |
| ⭐⭐⭐ | 一般，存在需要改进的地方 |
| ⭐⭐ | 较差，存在严重问题 |
| ⭐ | 不可接受，需要重写 |
